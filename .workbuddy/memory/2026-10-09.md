# 2026-10-09

## 排查：AI key 池「已禁用 key 仍被挑出」（401 日志 keyId=f443ed75…）

只做诊断，未改代码。结论：

- 查询**带**了 `enabled eq true`：`AiConfig.kt:67-71`（同时 `provider=10`）。漏条件的假设不成立。
- 全局 `KSqlClient` bean = `registry.sqlClient` = `writerSql`（JimmerConfig.kt:34 / ClusterRegistry.kt:44），
  `loadKeys` 走 writer，**不存在读写分离从库延迟**问题。
- 真实闸门是两道：①Redis 冷却（即时，1h）②内存列表 300s TTL（`AiApiKeyStore.REFRESH_TTL_SEC=300`，
  `cached()` L103-108）后才重载剔除。所以「禁用后短时间内又被 pick」只能发生在
  Redis 冷却没兜住时（MGET fail-open / 冷却 key 丢：重启、flush、主从切换、maxmemory 逐出）。
- 日志措辞会误导：`SpringAiScanRunner.kt:262-270` 的 `disableAttempted` 只代表没抛异常，
  `affected==0`（行已 enabled=false / 已删）照样打 "disabling (PG enabled=false, best-effort)"。
  是否真改到行要看伴生的 WARN "AI API key disabled (enabled=false)" 或 INFO "disable was a no-op"。
- 同步/异步 scan 都在事务外执行 AI（`ScanTaskService.doRun` 内 `scanRunner.run`，无 TxRunner 包裹），
  所以 disable 的 UPDATE 是 autocommit，**不存在被事务回滚**的可能（已排除）。
- 导入脚本 `scripts/agnes_keys/import_from_register.sh` 用 `ON CONFLICT (key) DO NOTHING`，不会把禁用 key 重新 enabled。

用户拍板选 A（本地剔除），已实施，见下节。

## 生产侧取证（同一件事，接上）

- 生产 PG：本机 `.env` 的 `PROD_PG`（jdbc 串，去 `jdbc:` 前缀直接喂 psql），走本地隧道 25432。
- 生产主机：`ssh app_us1`（端口 20856 已在本地 ssh config）；unit 是 **app-core-api.service**（不是 core-api）；
  env 文件 `/data/app/core-api/common/.env.prod`（变量名 `REDIS_URL`、`PG_*`，不是 SPRING_DATA_REDIS_*）；
  日志 `/data/app/log/core-api/{info,warn,error}.log`；部署槽 `/data/app/core-api/{a,b}` + `current` 软链。
- 生产实测：3169 行 = enabled 2316 / disabled 853。今天 15:39 UTC 有两笔批量 UPDATE（500+343 行）
  把 key 批量禁用（带 updated_at=now()），此后日志 "pool loaded. count=2316" 与 enabled 数一致。
- **验证结论**：应用的禁用 UPDATE 只写 `enabled` 列，**不动 `updated_at`**（10-07 被自动禁用的 8 行 updated_at
  仍是 bulk insert 时间）→ `updated_at` 不能用来推断禁用时间；updated_at 变了的禁用行基本都是人工/脚本 SQL 干的。
- Redis：`maxmemory=0` + `noeviction`（不会被逐出），但 `appendonly=no`、RDB 定时落盘、
  **uptime 只有 1 天 → 重启会丢冷却键**。单实例部署（`ss -ltnp | grep 3001` 只有一个 PID）。

## 实施（方案 A）

- `AiApiKeyStore`：`disableKeyFn` 签名改 `(String) -> Boolean`（true = DB 已确认不在 enabled 集合），
  新增 `evict()`；`disableKey()` = 写成功才剔除（写失败不剔除，避免好 key 白掉轮换位）。
- `AiConfig.disableKeyFn`：成功返回 true（含 affected=0 的重复禁用），异常返回 false。
- 测试：`AiApiKeyStoreTest` 加 3 个用例（禁用后立即不再被 pick / 写失败不剔除 / 剔除到空触发重载），
  全 sk 通过。**注意**：`AiConfigDisableKeyDbTest` 3 个用例在本机必失败——需要 Docker（本机 daemon 没起），
  非本次改动引入。
